# Nata's Kitchen 🍽️

Семейный кулинарный ассистент: мобильное веб-приложение без сборки (vanilla JS ES-модули + Firebase Firestore), хостится на GitHub Pages из `main` (мерж в `main` = автодеплой на прод за ~1 минуту).

Умеет: коллекция рецептов с распознаванием из фото/текста (GPT-4o), расчёт КБЖУ на порцию, «🎲 Что приготовить?» с фильтрами и веб-поиском новых рецептов, недельное меню с батч-кукингом и квотами ужинов, автосписок покупок, профиль семьи.

## Данные (Firestore, проект `natas-kitchen`)

Мульти-семейная модель (Фаза 5): пользователи входят через Google или email+пароль; `users/{uid}.householdId` привязывает аккаунт к семье. Семей может быть несколько (кейс владельца: она + сестра + родители), книга рецептов — одна общая. Онбординг нового пользователя: создать семью (генерируется 6-значный `joinCode`), присоединиться по коду или — для владельца — забрать легаси-семью `default` со всей историей (`claimLegacyHousehold`, доступно пока `ownerUid` не установлен).

- **`users/{uid}`** — маппинг пользователь → семья: `{ householdId, email, name }`.
- **`recipes/{slug}`** — общая книга рецептов (одна на все семьи):
  `{ id, emoji, title, meta, yield, servings?, note, tags[], ingredients[], steps[], attrs?, createdBy?, source?, sourceUrl?, needsReview?[] }`
  - Ингредиент: `{ n, a }` — исходный текст (не разрушается) + после миграции `qty`, `unit` (`g|ml|pcs|tbsp|tsp|pinch`), `ing` (канонический ключ), `opt`.
  - `attrs` — планировщик: `{ mealType[], mainProtein, cuisine, activeMin, totalMin, heaviness, spiciness, dietFlags[], kidFriendly }`.
  - `createdBy` — uid автора («default» — легаси до auth); **править/удалять может только автор**; легаси-рецепты — члены семьи `default`.
  - Регулярные рецепты несут `householdId` и **видны только своей семье** (чужие заготовки — шум); id пер-семейные `reg-<hid>-<название>`, легаси-семья сохраняет `reg-<название>`. Регулярный парсер пишет в **текущую** семью (в 👪 Семья показано, в какую); если рецепт осел не туда — на карточке кнопка «🏠 Переселить в другую семью» меняет `householdId` по коду приглашения (правило в firestore.rules разрешает менять только это поле члену текущей семьи рецепта).
  - Легаси-поля `timesCooked`/`lastCookedAt` на рецепте — только fallback, новые записи идут в recipeState.
- **`nutrition/{canonicalName}`** — справочник ингредиентов (глобальный, факты):
  `{ kcal, protein, fat, carbs, fiber?, potassium?, phosphorus?, unitG?, aliases?[], category?, isPantryStaple?, perishability?, storage? }` на 100 г. Клетчатка (г), калий и фосфор (мг) — опциональны; нужны для диабет/почечных семей. Заполняются отдельной кнопкой «🩸 Добавить клетчатку · калий · фосфор» на странице 🥗 (обычное «Заполнить отсутствующие» их не дозапрашивает — оно берёт только записи вообще без ккал; кнопка дозаливки перезапрашивает микроэлементы для уже заполненных записей и подмешивает только эти поля, не трогая ккал/Б/Ж/У).
- **`households/{hid}`** — профиль семьи: `{ name, members[{name,coeff}], planMeals[breakfast|lunch|dinner], rhythm{mon..sun: мин|null}, excludeText, dinnerQuota{meat,fish,veg}, regularDishesText, hideRegular, weekendFull, ownerUid, joinCode, substitutions[{from,to}], showMicros }`. `planMeals` задаёт будни; при `weekendFull` (по умолчанию true) суббота и воскресенье планируют все три приёма. `joinCode` показан в 👪 Семья — по нему присоединяются члены семьи. `substitutions` — пер-семейные замены продуктов (слой поверх общей книги, оригинал рецепта не трогается); `showMicros` включает показ клетчатки/калия/фосфора.
- **`households/{hid}/recipeState/{recipeId}`** — история готовки семьи: `{ timesCooked, lastCookedAt }` (оверлей поверх рецептов; легаси-поля на самом рецепте — fallback только для семьи `default`).
- **`households/{hid}/plans/{weekStartISO}`** — план недели: `{ weekStart, slots{slotId: {recipeId, locked, kind?: batch|reheat, linkedTo?}}, checked{}, notes{slotId: текст} }`; slotId = `mon_dinner` и т.п., weekStart = понедельник `YYYY-MM-DD`. `notes` — свободные заметки/комментарии к приёму пищи (кнопка 💬 сразу после названия блюда: гарнир, закуска, особое требование члена семьи), живут отдельно от слота и переживают реролл/генерацию. Кнопки замка в UI нет: `locked` ставится только ручным выбором из шторки и защищает слот от перегенерации.

## Ключевые бизнес-правила (заданы пользователем, зашиты детерминированно)

**Сытность (`effectiveHeaviness`, каскад, специфичное раньше общего):**
1. >550 ккал или >25 г жира на порцию → сытное (данные сильнее эвристик)
2. Супы: без мяса → лёгкие (рыба/морепродукты — не мясо); с мясом → средние; мясо + бобовые (фасоль/чечевица/нут/горох) → сытные
3. Салаты: без мяса → лёгкие; с любым мясом → средние
4. Свинина/бекон/колбаски/говядина/фарш/баранина, куриные-утиные-индюшачьи ножки и бёдра → сытное; **любая паста** → сытное
5. Рыба/морепродукты и куриная/индюшачья грудка → среднее
6. Овощное/молочное с ≤400 ккал и ≤20 г жира → лёгкое; выпечка лёгкой не бывает
- Десерты и мороженое **вообще не попадают** в выдачу подбора/планировщика.
- Детекция по названиям ингредиентов и блюда — работает и на немигрированных рецептах. ⚠️ `\b` в JS не ловит кириллицу — используются `(^|\s)`-группы.

**Батч-блюда (`isBatchDish`) — «готовим раз — едим три»:** оладьи/вафли/маффины, творожные и овощные запеканки, драники, сырники, чизкейки, винегрет/оливье/сельдь под шубой, рассольник, щи; мясные/птичьи рагу и соусы (гуляш, бефстроганов, жаркое, оссобуко, карри…); супы с мясом и грибные; мясо/птица в томатном соусе. В плане: слот готовки «×N + ❄ заморозка» (N = (2×порции семьи + 1)/выход, шаг 0.5) + связанный слот разогрева ♨ на следующий день (завтрак→завтрак, ужин→обед либо ужин); закупка умножает готовку и не считает разогрев. **Не больше одного разогрева в день** (`dayHasReheat`) — ни авто-разогрев батча, ни ручной; иначе день целиком из вчерашнего.

**Ручной «♨ Разогреть» на слоте:** кнопка ♨ подставляет в слот вчерашнее приготовленное блюдо как разогрев (`pickReheatSource`: ужин → обед → завтрак предыдущего дня, не сам разогрев); слот закрепляется. Блокируется, если в этот день разогрев уже есть, или если вчерашнего блюда нет (понедельник/пусто).

**Подбор («Что приготовить?» и неделя):** скоринг по давности готовки (недавнее штрафуется, ни разу — умеренная новизна) + взвешенный случайный из топ-5; сытность и продукты-исключения — жёсткие фильтры, не ослабляются (кроме: указанные продукты побеждают сытность с переездом бегунка); лимит времени ослабляется с пометкой; «из каких продуктов» — 1–2 продукта → хотя бы один, 3+ → хотя бы два, морфологичное сопоставление (кабачки↔кабачок, фраза целиком).

**Квоты ужинов:** dinnerQuota — сколько мясных/рыбных/вегетарианских ужинов в неделю; классы не идут подряд (кроме разогрева), свежие мясные чередуются средний↔сытный; разогрев батча в ужин расходует квоту, при исчерпании — не ставится (порции в заморозку).

**Замены продуктов и микроэлементы (диабет/почки):** в 👪 Семья семья задаёт правила замен `продукт → замена` (мука → цельнозерновая, сахар → эритрит, белый рис → бурый). Замены — **слой поверх общей книги** (`substitute.js`): в карточке рецепта, расчёте КБЖУ и списке покупок продукт показывается заменённым (с пометкой «↺ вместо…»), но сам рецепт в общей книге не меняется — у других семей он прежний, редактор всегда правит оригинал. Панель КБЖУ ведёт цифру **на порцию**: поле «Порций в блюде» подставляется из `servings` рецепта (можно поменять), КБЖУ и микроэлементы делятся на это число живьём; пусто — показывается на всё блюдо. Чекбокс «показывать клетчатку/калий/фосфор» добавляет на порцию чистые углеводы (углеводы − клетчатка), калий и фосфор; «≥» означает, что часть ингредиентов без данных и сумма неполная. Справочник обогащается этими полями через «🏷️ Обогатить»/«✨ Узнать».

**Регулярные блюда — основа недели:** в 👪 Семья есть текстовое окно «привычные блюда» — семья свободным текстом описывает еду, которую готовит из головы без рецептов. Кнопка «✨ Создать рецепты» через GPT превращает описание в 5–10 (или сколько указано, 1–15) примитивных рецептов с тэгом «🔁 Регулярные» (id стабильные `reg-<название>` — повторный разбор перезаписывает, а не дублирует). Чекбокс `hideRegular` скрывает их из общего списка (виден только таб «🔁 Регулярные»). В планировщике недели регулярные — основа: блюда из основной базы попадают в план дозированно, по умолчанию 2–4 в неделю (`baseWeekTarget` = clamp(слоты/3, 2..4)), равномерно распределённые по свободным слотам; залоченные базовые расходуют этот лимит; если в нужном пуле пусто — честный fallback в другой пул, слоты не пустуют. **Поле «Ужинов из книги в неделю»** (`baseDinnersPerWeek`, 👪 Семья) задаёт точное число: тогда базовые блюда идут ТОЛЬКО в ужины и ровно столько (`baseDinnersSetting`), для ужинов кросс-пул отключается (жёсткая квота, лишние ужины — регулярные с повтором, а не из книги); пусто — авто. 0 → неделя без блюд из книги. Реролл сохраняет происхождение блюда (регулярное → регулярное, базовое → базовое), пустой слот пополняется из регулярных.

**Разнообразие белка и гарнира:** у комбо-рецептов «Белок + гарнир» есть ключ белкового приёма (`proteinKey` = белковая часть, напр. «белая рыба на пару») и ключ гарнира (`sideKey`, напр. «киноа»). Планировщик не готовит один и тот же белок **или** гарнир свежим повторно за неделю — иначе рыба попадала в меню 4 раза с разными гарнирами, а киноа лезла в каждый слот. Второй раз блюдо появляется только разогревом вчерашнего (тот же рецепт-батч). Откат ступенчатый: если разнообразных пар не хватает, сначала ослабляется ограничение по гарниру (белок остаётся разным), потом по белку, и лишь в самом конце — оба, чтобы слот не остался пустым. Реролл тоже не подставляет белок/гарнир, уже занятый в других слотах.

**Случайный выбор, а не алфавит:** у регулярных блюд без истории готовки скор одинаковый — раньше стабильная сортировка давала алфавитную выдачу («Бефстроганов из индейки», затем «из говядины»). Теперь в `pickSuggestion` добавлен случайный тай-брейк (`j = rand()`), так что при равном скоре порядок действительно случайный (в тестах `rand=()=>0` — стабильный). Плюс по вечерам подряд не предлагаются блюда, соседние с вчерашним ужином по каталогу (±2 в алфавитном списке) — мягко: если в пуле не осталось несоседних, ограничение снимается и слот не пустеет, в чужой пул из-за него не уходим.

**GPT sanity-check меню (поверх алгоритма):** меню строит детерминированный планировщик; кнопка «🤖 Проверить» на экране недели отправляет готовое меню в GPT (`js/menucheck.js`) — он проверяет на разнообразие и возвращает список слотов на замену (не белок всю неделю, не один гарнир по пять раз, чередование злаков/овощей; если на обед разогрев вчерашнего — завтрак того же дня должен быть свежим). GPT **не придумывает блюда** — отмеченные слоты перекатывает наш `rerollSlot`, соблюдающий разнообразие; закреплённые слоты и разогревы не трогаются. Промпт проверки полностью редактируется на **админ-странице** (👪 Семья → «⚙️ Промпт проверки меню»), хранится в профиле семьи (`menuCheckPrompt`), «↩️ Сбросить» возвращает стандартный.

**Очистить все регулярные:** кнопка «🗑 Очистить все регулярные рецепты» на табе «🔁 Регулярные» (над списком) и в 👪 Семья — разом удаляет все регулярные рецепты семьи (и привычные, и комбо), которые семья вправе править; чужие легаси остаются, о чём сообщается.

**Белок + гарнир (чередование):** кнопка «🍱 Белок + гарнир, чередовать» под тем же описанием привычных блюд в 👪 Семья — ассистент сам раскладывает блюда на белок и гарнир, **даже если они названы вместе** («гречка с курицей», «рыба с картошкой»). GPT возвращает два списка РАЗНЫХ компонентов (дубли схлопываются — один и тот же гарнир/белок из разных пар остаётся один раз), а дальше **детерминированный код** (`js/combo.js`) собирает допустимые пары и материализует их как регулярные рецепты «Белок + гарнир» — так планировщик уже умеет их ротировать, считать покупки/КБЖУ и печатать. Правила сочетаемости (заданы владельцем, зашиты в код с тестами): рыба/морепродукты **не** идут с пастой; бобовым нужны овощи, **а не** крупы/картошка (сама бобовая часть — уже крахмал+белок). Сборка «на разнообразие»: жадно чередует и белок, и гарнир по конкретным блюдам и категориям, без повторов подряд; классификация компонента по названию (крахмал/овощ, класс белка) работает и когда GPT не проставил категорию. Поле «Комбинаций» ограничивает количество (иначе все допустимые пары).

**Список покупок:** канонизация ключа (alias справочника → «или…» → прилагательные-модификаторы → группы яйца/яйцо/яиц), штучные товары (есть unitG) покупаются штуками с округлением вверх, pantry staples исключаются, группировка по категориям, чекбоксы в плане.

```bash
npm test     # node --test, 106 тестов, без зависимостей
npx serve .  # локально; file:// не работает (ES-модули)
```

Смоук-тесты в разработке гонялись через Playwright с мокнутыми Firestore/OpenAI (см. историю PR). Прод: GitHub Pages деплоит `main` автоматически.

## Ручные шаги, которые может сделать только владелец

0. **Перед тестом трёх семей (ОБЯЗАТЕЛЬНО, иначе вход не заработает):**
   - Firebase Console → Authentication → Sign-in method → включить **Google** и **Email/Password**;
   - Authentication → Settings → Authorized domains → добавить `natalyatsarapaeva-tech.github.io`;
   - задеплоить `firestore.rules` (Console → Firestore Database → Rules) — без них база всё ещё в test mode и любой может писать;
   - войти самой ПЕРВОЙ и нажать «Это моя семья — забрать» в онбординге: легаси-семья `default` со всеми рецептами, историей и планами станет твоей, появится код приглашения для мужа/детей. Мама и сестра создают свои семьи сами.
1. ~~Firestore rules~~ — см. пункт 0.
2. **Миграция рецептов**: 🥗 → «🔧 миграция рецептов» → Сканировать → Мигрировать через GPT → снять жёлтые «проверить». Без неё работают fallback'и (категории/парсинг meta), но точность ниже и нет ккал/порцию.
3. **Обогащение справочника**: страница 🥗 → «🏷️ Обогатить» (категории, staple, хранение — нужны списку покупок).
4. **Профиль семьи**: 📅 → 👪 — члены, приёмы, время по дням, исключения, квоты ужинов.
5. **Ключ OpenAI** вводится в браузере (localStorage); до публичного релиза нужен серверный прокси.
