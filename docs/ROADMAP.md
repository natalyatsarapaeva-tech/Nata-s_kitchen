# Roadmap: от коллекции рецептов к домашнему кулинарному ассистенту

Цель — полноценный домашний ассистент для семьи или одного человека, который готовит дома
и/или держит определённую диету: планирование недели, батч-кукинг, список покупок,
диетические цели, идеи «что приготовить сегодня», обмен с семьёй.

Основа — [спецификация планировщика v0.1](mealplanner-spec-v0.1.md).
Её ключевые архитектурные решения приняты; часть функций сокращена или перенесена
в поздние фазы (см. «Отклонения от спеки» внизу).

Комментарий к приёму (бывший «＋») теперь 💬 сразу после названия блюда
- ✅ **Ужинов из книги в неделю (настройка)**: поле в 👪 Семья (`baseDinnersPerWeek`) — точное число ужинов из основной кулинарной книги; базовые идут только в ужины и ровно столько (`baseDinnersSetting`), для ужинов кросс-пул отключается; пусто — авто (2–4), 0 — без блюд из книги

**Тесты**: 141 в `npm test` (чистые модули suggest/planner/nutrition-core/utils/regular/combo). Смоуки — Playwright с мокнутыми Firestore/OpenAI.

**Принятые архитектурные решения** (обсуждены с владельцем, менять только по её слову):
1. **Иерархия для auth**: «Кулинарные книги» (коллекции рецептов) и «Семьи» (households) — равноправные сущности, many-to-many через подписку. Рецепты живут в книге (не копируются между семьями), пер-семейное состояние (история, вердикты, планы) — в household. Кейс владельца: одна книга ↔ три семьи (её с 2 детьми-малоежками; сестра с 3 детьми; родители с диабетико-почечной диетой папы).
2. **Править рецепт может только автор** (`createdBy`); остальные читают/копируют.
3. **Порядок**: планировщик доделывается ДО auth на `households/default`; при auth добавляется только маппинг user→household + rules, схема не меняется.
4. LLM только на краях (разметка/поиск/объяснения), вся логика детерминированная; правила сытности/батча/квот — от владельца, зашиты в код с тестами.

**Ручные шаги владельца, ещё не сделанные** (см. README «Ручные шаги»): деплой firestore.rules, прогон миграции рецептов, обогащение справочника, заполнение профиля семьи.

**Следующие кандидаты** (по приоритету обсуждений):
1. **Морозилка как инвентарь** (вторая половина Фазы 2): ❄-порции создаются при «✓ приготовил» батч-слота, размещаются в будущие недели первыми (шаги 2.2.1–2.2.2 спеки)
2. **Масштабирование всей недели** под коэффициенты членов семьи (порции ≠ выход рецепта)
3. **Фаза 3**: диетические цели (ккал/белок per member, пресеты весов, «неделя отстаёт по белку»)
4. **Остаток Фазы 5**: серверный прокси OpenAI (обязателен до чужих людей, семье хватает ключа в браузере), realtime-список покупок, familyVerdicts, PWA

**Рабочий процесс с ассистентом**: ветка `claude/recipe-app-review-architecture-dvngdw`; после каждого squash-merge ветку нужно ребейзить `--onto origin/main <последний-до-squash-коммит>` (иначе PR конфликтует). Мерж — только по явному «Merge» владельца; после мержа проверить успех «pages build and deployment» на коммите мержа.

**Принятая архитектура (из спеки, подтверждаю):**
- Детерминированный планировщик с ограничениями строит план; **LLM работает только на краях** —
  разметка рецептов при импорте, перевод свободных пожеланий в модификаторы, реранк и объяснения.
  LLM никогда не считает порции и не нарушает аллергии.
- КБЖУ считается из справочника ингредиентов, а не «на глаз» LLM — уже так и работает,
  LLM нужен только для маппинга «2 луковицы» → ингредиент + граммы.
- Планировщик выполняется на клиенте (обычный JS, данные в Firestore) — сервер не нужен
  до фазы шаринга.

## ✅ Фаза 0 — Фундамент данных *(СДЕЛАНО, PR #2)*

Сейчас ингредиенты — свободные строки `{n:'Морковь', a:'2 шт'}`, выход — свободный текст
(«4 порции»). Планировать на этом нельзя. Ничего из фаз 1+ не строится, пока нет:

1. **Структурированные ингредиенты**: `{ingredientId, rawText, qty, unit, optional}` —
   `rawText` сохраняем всегда, пользовательский ввод не разрушаем. Единицы: `g | ml | pcs | tbsp | tsp | pinch`.
2. **Числовое поле `servings`** + КБЖУ на порцию (сейчас только на весь рецепт).
3. **Апгрейд справочника ингредиентов** (коллекция `nutrition` → `ingredients`):
   синонимы («томат» = «помидор» — сейчас это два разных ключа), категория,
   `isPantryStaple` (соль/масло/мука не попадают в список покупок), класс скоропортящести,
   способ хранения. Существующие данные КБЖУ мигрируют как есть.
4. **Страница миграции** (`tools/`): GPT батчами разбирает свободный текст существующих
   рецептов в структуру, пользователь подтверждает сомнительные позиции. Поля с низкой
   уверенностью — не отдельные confidence-флоаты на каждое поле, а один список
   `needsReview` на рецепт (упрощение спеки, см. ниже).
5. **Импорт-пайплайн** (фото/текст) сразу выдаёт новую схему + дешёвый и ценный минимум
   AI-тегов: `mealType`, `mainProtein`, `activeMin/totalMin`, `heaviness`, `spiciness`,
   `dietFlags`, `kidFriendly`, `cuisine`.

## ✅ Фаза 1 — MVP-планировщик *(СДЕЛАНО, PR #2–#8: кубик, неделя, профиль, покупки, квоты)*

Первым релизом — самое короткое: **кнопка «идея на ужин»**: тот же скоринг на один слот
(фильтр по типу приёма + «давно не готовили» + бюджет времени), карточка, реролл.
Требует только `lastCookedAt` и тегов из фазы 0. Это витрина ценности за неделю работы.

Затем полный недельный цикл:

- **Профиль-лайт** (`household`, пока один документ без auth): члены семьи с коэффициентами
  порций, аллергии (жёсткий фильтр), нелюбимое (штраф в скоринге), `weeklyRhythm`
  (бюджет времени на ужин по дням, какие приёмы планируем), `repeatTolerance`.
- **Генератор**: типизация слотов (шаг 2.1 спеки) → пул кандидатов из своих рецептов
  (шаг 2.3, без builtin/web) → жадное заполнение по датам с **упрощённым скорингом из
  4 весов**: preference, time_fit, variety (анти-повторы белка/кухни/техники), freshness_window.
  Проверки недели: только жёсткие D (время по дням) и E (повтор белка).
- **UI недели**: сетка на 7 дней, на слоте — reroll / замена вручную / замок;
  объяснения слотов шаблонные («быстрый ужин — у тебя вторник загружен»), не LLM.
- **Список покупок**: сумма ингредиентов × порции − pantry staples, округление до
  типичной упаковки, группировка по категориям, чекбоксы в магазине. Живёт в документе плана.
- **Сигналы**: «приготовил» (`timesCooked`, `lastCookedAt`), «пропустил» (`timesSkipped`) —
  собираем с первого дня, использовать начнём в фазе 4.

## 🔶 Фаза 2 — Батч-кукинг *(батч-якоря СДЕЛАНЫ в PR #6; осталось: инвентарь морозилки, lifecycle-разметка, repair loop)*

«Приготовь один раз — поешь три» — согласна со спекой, что это то, чего нет у конкурентов
в юзабельном виде. Порядок внутри фазы важен: сначала разметка, потом логика.

- **Lifecycle-разметка**: `fridgeDays`, `freezable`, `freezerMonths`, `reheatQuality`,
  `improvesNextDay`, `easilyScalable`, `maxReasonableBatch`. Новые рецепты — LLM + подтверждение
  при импорте; существующие — батч-прогон через страницу миграции.
- **Батч-якоря** (шаг 2.4): в день с временем — готовим ×N, планировщик сам решает
  сколько съесть / в холодильник / в морозилку, связанные слоты разогрева
  (`improvesNextDay` → разогрев ставится на следующий день).
- **Инвентарь, выведенный из плана, а не вводимый руками** (ключевое отклонение от спеки):
  заморозки и остатки создаются автоматически при отметке «приготовил» батч-слота
  (1 тап подтверждения), морозилка/остатки размещаются в новые недели первыми
  (шаги 2.2.1–2.2.2). Ручной учёт открытых упаковок (2.2.3) — не делаем, см. ниже.
- **Repair loop** (шаг 2.8) в упрощённом виде: свапы по мягким нарушениям, максимум 5 итераций,
  честное сообщение о неразрешимом конфликте.

## Фаза 3 — Диета и цели питания

Тот же солвер, другие веса — «построй диету на X ккал/день» не отдельная фича,
а режим планировщика:

- Цели питания per member (ккал, белок…), **goal-пресеты** → веса скоринга
  (`weight_loss` поднимает nutrition_fit и лёгкие блюда, `minimal_effort` — time_fit и т.д.).
- Недельные проверки A/B/F (ккал ±10%, белок, доля овощей) в repair loop.
- Дашборд дня/недели: факт vs цель по КБЖУ, «неделя отстаёт по белку» → буст
  высокобелковых кандидатов в оставшихся слотах.
- Свободное пожелание текстом («хочу больше рыбы», «на этой неделе совсем нет времени») →
  LLM переводит в модификаторы скоринга/оверрайды (вход шага 2.0) — первая LLM-задача
  в рантайме планировщика, узкая и безопасная.

## Фаза 4 — Обучение на поведении и «человечность»

- **Фидбек-цикл** (2.11): вечерний 1-тап «приготовил / пропустил (почему)», рейтинг после
  готовки; 2 пропуска подряд снижают приоритет; раз в месяц тихая рекалибровка
  cooldown и exploration по фактическому поведению.
- **LLM-реранк** (2.9): проверка готового плана на нелепости (три супа подряд),
  swap-предложения валидируются солвером; генерация человеческих объяснений слотов.
- **Синергия ингредиентов** (w6): предпочитать рецепты, разделяющие скоропорт с уже
  поставленными блюдами — это дешёвые 80% ценности «цепочек остатков» без их сложности.
- **Exploration**: встроенная база рецептов / импорт из веба как источник новых кандидатов
  (`explorationRatio`), знакомые кухни/белки в приоритете.

## Фаза 5 — Семья и публикация *(здесь возвращается auth)*

- Firebase Auth + household-доступ: общий план, общий список покупок в реальном времени
  (killer-фича для семьи — Firestore даёт её почти бесплатно), `familyVerdicts`
  per member («ребёнок отказался» — штраф в скоринге).
- Серверный прокси для OpenAI (Cloud Function), деплой security rules — обязательны
  до любого стороннего пользователя.
- PWA/офлайн, режим готовки (шаги на весь экран, wake-lock), шаринг рецепта ссылкой.

## Отклонения от спеки и обоснование

| Спека | Решение | Почему |
|---|---|---|
| Экономика: cost_estimate, ценовой справочник, perishable_share, акции | **Отложено за фазу 5** (опционально — грубый `costTier` от LLM) | Ценовая база регионально-специфична и является отдельным продуктом; без неё поля мертвы. Не критично для цели «ассистент готовки/диеты» |
| Per-step разметка: `equipment`, `can_pause_after`, `is_active` на каждый шаг | **Сокращено** до `activeMin`/`totalMin` на рецепт | Стоимость разметки высокая, планировщику достаточно агрегатов; вернуться при появлении режима готовки (фаза 5) |
| Цепочки остатков «суп из вчерашней курицы» (2.5) | **Отложено**, вместо них — синергия ингредиентов (фаза 4) | AI-разметка «рецепт использует остатки блюда X» ненадёжна; разделение скоропорта между блюдами даёт большую часть ценности детерминированно |
| Ручной инвентарь `open_perishables` (2.2.3) | **Не делаем**; инвентарь выводится из исполнения плана | Ручной учёт остатков — классическая причина смерти планировщиков: пользователи перестают его вести, план начинает врать |
| `confidence: float` на каждое AI-поле | **Упрощено** до списка `needsReview` на рецепт | Та же UX-механика подтверждения («это можно заморозить?») без удвоения схемы |
| `substitutes` per ingredient | **Отложено** | Штрафы за dislikes покрывают основной сценарий; замены — после фидбек-цикла, когда появятся данные `times_substituted` |
| 9 весов скоринга сразу | **4 веса в MVP** → +nutrition/cost/synergy/exploration по фазам | Каждый вес нужно калибровать на реальном поведении; 9 некалиброванных хуже 4 осмысленных |
| Builtin-база с редакторской разметкой в MVP | **Перенесено в фазу 4** | До неё планировщик работает на собственных рецептах пользователя — их уже ~30+ и они любимые; это честнее для «личного» этапа продукта |

Что в спеке особенно правильно и сохранено без изменений: разделение солвер/LLM,
lifecycle-блок как ядро батч-логики, `weekly_rhythm` как ядро персонализации,
`times_skipped` как сильный негативный сигнал, аллергии = жёсткий фильтр /
нелюбимое = мягкий штраф, честное сообщение о неразрешимых конфликтах вместо тихого нарушения целей.
